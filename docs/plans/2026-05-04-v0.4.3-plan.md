# v0.4.3 Plan — `update` subcommand + tightened vocabulary

> **Status: drafted 2026-05-04.** Awaiting Plan-agent critique before execution.

## 1. Theme

Single-trigger upgrade ergonomics. v0.4.0–v0.4.2 built every preservation mechanism a downstream-project upgrade needs (cleanliness gate, auto-backup, marker-guided merge, migration sentinels, UPGRADE_NOTES auto-archive, byte-equivalent restore). v0.4.3 wraps those layers behind a single `update` subcommand and tightens the user-vocabulary contract in PROTOCOL.md so agents and humans both have one canonical entry point.

**Critical clarification.** `update` introduces ZERO new preservation mechanisms. Every safety layer already exists in v0.4.2. v0.4.3 adds:

- A pre-flight version check + interactive confirmation prompt around `init`'s existing upgrade mode.
- One genuinely new piece of state-management: `update --rollback` must clean up `.collab/.migrations/` sentinels for migrations that the rollback reverses (otherwise the next `update` skips migrations because sentinels say "applied" while VERSION says pre-upgrade — a real correctness bug for non-trivial future migrations).
- A `version_le` helper in a shared lib so the orchestration script doesn't have to source or re-exec just to compare versions.

Net code-add estimate: **250–400 lines of bash** for `collab-update.sh`, plus ~30 for `scripts/lib/semver.sh`, plus tests. Not a 50-line wrapper. The framing "thin orchestration" was retracted after Plan-agent critique surfaced realistic scope.

## 2. Scope decisions

- **Option A** (`update` subcommand) and **Option C** (vocabulary tightening) — both in v0.4.3. Option B (per-platform slash commands) deferred to v0.5.0+.
- **Confirmation prompt is interactive by default.** `--yes` flag opt-in for non-interactive contexts (CI, scripts).
- **`--diff-first` is OFF by default.** Opt-in via flag. Rationale: industry pattern (brew, apt, npm all default OFF; preview is opt-in via `--dry-run` etc.); migration body's `>>> Upgrade summary` blocks already emit inline summaries; layered safety nets make full-diff preview redundant for typical patch jumps; 2x runtime cost on Windows is non-trivial.
- **Scope size: borderline-feature in a patch number.** v0.4.3 adds a new public CLI surface (`update` subcommand). Strictly read, this is minor-version territory. Treating as patch since:
  1. Pre-1.0 framework — version semantics are owner's call.
  2. Implementation is purely additive: new command, no behavior change to existing commands.
  3. Underlying mechanism (init upgrade mode) is unchanged — only orchestration.
  4. User explicitly authorized v0.4.3 framing.
- **Cross-platform**: bash + cli.js shim only. Slash commands for Claude Code / Codex / Gemini deferred.

## 3. Group 1 — `update` subcommand

### 3.1 `scripts/collab-update.sh` (new)

Modes (mutually exclusive):

| Invocation | Behavior |
|---|---|
| `update` (default) | Pre-flight check + confirm + apply + post-flight reminder |
| `update --check` | Pure check mode — print "installed X, latest Y, run `update` to upgrade." Exit 0. No state changes. |
| `update --ack` | Archive `.collab/UPGRADE_NOTES.md` (delegates to `init --ack-upgrade`). Print final `collab-check` state. |
| `update --rollback` | Restore from latest backup (delegates to `init --restore latest`). |

Modifier flags (additive on default mode):

| Flag | Effect |
|---|---|
| `--yes` / `-y` | Skip the confirmation prompt. Required for non-interactive contexts. |
| `--diff-first` | Run `--diff` preview pass before applying. User confirms a SECOND time after seeing diffs. Adds ~migration runtime overhead. |
| `--no-backup` | Passed through to `init` upgrade mode. Disables auto-backup. NOT recommended for normal use. |
| `--force-dirty` | Passed through to `init`. Skips the cleanliness check. |

Pre-flight check (default mode):

```
$ update
Multi-agent-collab framework update
  Installed: 0.4.0
  Latest:    0.4.2
  Migrations to run: 2 (0.4.0→0.4.1, 0.4.1→0.4.2)
  Auto-backup will run before any changes.

Continue? [Y/n]:
```

Pre-flight order of operations:

1. **Bootstrap check.** If `.collab/VERSION` does not exist, print `update: this repo is not bootstrapped. Run 'init' first.` and exit non-zero. Don't try to upgrade what isn't there.

2. **Read installed version.** `cat .collab/VERSION`. If garbage (non-semver), print the same hard-fail message that `init`'s G6 produces and exit. (Note: detect_mode validates this; `update` MUST do the same check before its own logic, since `update` may exit before invoking init.)

3. **Read shipped version.** `cat "$SKILL_ROOT/templates/collab/VERSION"`. `$SKILL_ROOT` is `$HERE/..` — same resolution as `collab-init.sh:8-10`. Works for skill-source AND npm-installed (bin/ + scripts/ + templates/ ship side-by-side per `package.json` files array).

4. **Compare.** Use `version_le` from `scripts/lib/semver.sh` (new — see §3.1.5).
   - If `installed == shipped`: print `Already up to date (<version>).` Exit 0.
   - If `installed > shipped` (numeric, not lex): print `Installed version <X> is newer than shipped <Y>. Nothing to do.` Exit 0.
   - Otherwise: continue.

5. **Compute migrations to actually run.** Walk identically to chain runner at `collab-init.sh:1043-1071`:
   ```bash
   from="$installed"
   to_run=()
   for script in "$HERE/migrations/"*-to-*.sh; do
     base=$(basename "$script" .sh)
     src="${base%-to-*}"; dst="${base##*-to-}"
     [[ "$src" == "$from" ]] || continue
     version_le "$dst" "$shipped" || continue
     # Sentinel-aware: skip migrations already applied per current SHA.
     if is_migration_applied "$src" "$dst" "$script"; then
       from="$dst"
       continue
     fi
     to_run+=("$src→$dst")
     from="$dst"
   done
   ```
   This produces the SAME set the chain runner will execute. The display count is "Migrations to RUN" (sentinel-filtered), not "would-have-run." If `to_run` is empty after this walk, the upgrade is effectively a re-init pass — print `Already at latest behavior (sentinels show all migrations applied). Re-init only.` and either exit 0 OR proceed silently. Recommendation: proceed (re-init is cheap and refreshes managed sections).

6. **Display + confirm.** If interactive, prompt as shown above. If `--yes` or `--diff-first`, skip the prompt (see §3.1.2 for `--diff-first` UX correction).

`is_migration_applied` is sourced from `collab-init.sh` — but to avoid sourcing the whole script (which executes top-level dispatch), it's extracted into `scripts/lib/migrations.sh` along with `version_le`, `collab_sha256` (already extracted in v0.4.2 G8). See §3.1.5.

### 3.1.1 Confirmation prompt spec

Verbatim implementation (handles all common reply forms; defaults Yes on empty input):

```bash
prompt_confirm() {
  local msg="${1:-Continue?}"
  if [[ ! -t 0 ]]; then
    echo "update: confirmation required (non-tty detected); pass --yes for non-interactive contexts" >&2
    exit 2
  fi
  local reply
  read -r -p "$msg [Y/n]: " reply
  case "${reply:-y}" in
    [Yy]|[Yy][Ee][Ss]) return 0 ;;
    *) return 1 ;;
  esac
}
```

`-t 0` (stdin) — NOT `-t 1`. Pipes on stdout are common in CI and not a signal of "no human present"; pipes on stdin (e.g. `echo y | update`) are how tests inject input. So we only fail-fast when stdin is non-interactive AND no `--yes` was passed.

SIGINT handling: bash's default ^C terminates the script with non-zero exit. Don't trap. Tests that pipe input never see SIGINT.

### 3.1.2 Apply phase

- If `--diff-first` was set, defer prompting (see §3.1.3 below). Otherwise:
  - With `--yes`: skip prompt, proceed.
  - Without `--yes`: call `prompt_confirm "Continue?"`. Decline (`n`/garbage) → exit 0 (no changes).
- Invoke `bash "$HERE/collab-init.sh"` with passed-through flags (`--no-backup`, `--force-dirty` if set). The full init upgrade flow runs unchanged.
- Re-exec rather than source. `collab-init.sh` runs top-level dispatch; sourcing executes that dispatch. Re-exec is the safe, supported pattern.

### 3.1.3 `--diff-first` UX

Single-confirm flow (corrected from initial draft after Plan-agent critique):

1. Pre-flight version check + migration count display (no prompt yet).
2. Run `bash "$HERE/collab-init.sh" --diff`. Print the diff hunks. (No state change to repo per M4.)
3. Prompt: `prompt_confirm "Apply these changes?"`. Decline → exit 0.
4. Confirm → run `bash "$HERE/collab-init.sh"` for real.

The user is prompted ONCE (after seeing the diff), not twice. The pre-flight prompt is suppressed when `--diff-first` is set because the diff display IS the user's preview-and-confirm material.

### 3.1.4 Post-flight

After init returns 0:
- If `.collab/UPGRADE_NOTES.md` exists (i.e., a non-empty migration ran): print `Upgrade complete. Read .collab/UPGRADE_NOTES.md and run the post-upgrade ritual, then run: update --ack`.
- If file absent (re-init only, no migrations ran): print `Re-init complete. No upgrade notes generated.` Exit 0 either way.

### 3.1.5 New shared lib `scripts/lib/semver.sh`

Extract the existing `version_le` from `collab-init.sh:618-628` into its own lib so `collab-update.sh` can source it without dragging in init's full body.

```bash
#!/usr/bin/env bash
# Numeric three-part semver compare. Inputs MUST be valid semver X.Y.Z.

version_le() {
  local a="$1" b="$2"
  local a1 a2 a3 b1 b2 b3
  IFS=. read -r a1 a2 a3 <<< "$a"
  IFS=. read -r b1 b2 b3 <<< "$b"
  if (( 10#$a1 < 10#$b1 )); then return 0; fi
  if (( 10#$a1 > 10#$b1 )); then return 1; fi
  if (( 10#$a2 < 10#$b2 )); then return 0; fi
  if (( 10#$a2 > 10#$b2 )); then return 1; fi
  if (( 10#$a3 <= 10#$b3 )); then return 0; fi
  return 1
}

version_lt() { ! version_le "$2" "$1"; }
version_eq() { [[ "$1" == "$2" ]]; }
```

Modify `scripts/collab-init.sh` to source `scripts/lib/semver.sh` and DELETE its inline `version_le`. Keeps the function in one place.

For `is_migration_applied`, similar treatment: extract from `collab-init.sh:687-720` into `scripts/lib/migrations.sh`. `collab-update.sh` sources both libs.

### 3.1.6 `--rollback` mode (CRITICAL — sentinel cleanup)

The naive approach (`bash init --restore latest`) is INCORRECT. After restore:
- `.collab/VERSION` reverts to e.g. 0.4.0
- `.collab/.migrations/0.4.0-to-0.4.1.applied`, `.4.1-to-.4.2.applied`, `.4.2-to-.4.3.applied` REMAIN (G4 prunes by INDEX-tracked paths; sentinels aren't INDEX-tracked).
- Next `update` reads sentinels with valid SHAs → `is_migration_applied` returns true for all → migration bodies SKIPPED → `re_init_shared` runs → VERSION written to shipped.
- Net: VERSION advances to shipped without migration bodies executing. **Real correctness bug for any future migration that does file work.**

Required fix in `update --rollback`:

1. Check `.collab/backup/` has at least one snapshot. If empty: `update: no backup to restore from; nothing was changed.` Exit 0.
2. Identify the latest backup directory (by mtime, same logic as `init --restore latest`).
3. **Parse `<from>` from the backup directory name** (`0.4.0-to-0.4.3-<stamp>` → `from=0.4.0`).
4. Invoke `bash "$HERE/collab-init.sh" --restore latest` (existing behavior — restores files, prunes migration-created files per G4).
5. **Sentinel cleanup** (NEW): after the restore, walk `.collab/.migrations/*.applied`. For each sentinel `<src>-to-<dst>.applied`, if `version_le "$from" "$src"` is FALSE (i.e. `src > from` — sentinel is for a migration that was rolled back), delete the sentinel.
6. Print: `Rolled back to <from>. Removed N stale sentinel(s).`

This requires `version_le` (which is now in the shared lib). The cleanup is small (~20 lines) but the correctness consequence is large.

### 3.1.7 `--ack` mode

- Invoke `bash "$HERE/collab-init.sh" --ack-upgrade` (existing — also auto-prunes old backups beyond `keep_recent_backups: 5`).
- After ack succeeds, run `bash "$HERE/collab-check.sh"` and print result.
- If `update --ack` is invoked when no `UPGRADE_NOTES.md` exists, the underlying `--ack-upgrade` exits 0 with `nothing to do`. That's fine; `update --ack` inherits.

### 3.1.8 `--check` mode

Cache-only by design (no network call). Read `.collab/.update-cache` (format documented at `collab-check.sh:155-178`):

- If file absent: print `Latest: unknown (run 'collab-check' to refresh)`. Don't fail.
- If file contains a valid semver: that's the cached "latest". Display it.
- If file contains `check-failed: <epoch>`: skip — print `Latest: unknown (last check failed)`. Display the cached fail timestamp if useful.
- Note: the cache TTL is 24h. If older, the value may be stale. `--check` does NOT refresh. Recommendation in `--help` text: `for fresh latest version, run: bash scripts/collab-check.sh`.

Future enhancement (deferred to v0.5.0): `update --check --refresh` to force a network query before reporting.

## 4. Group 2 — Vocabulary tightening (Option C)

`templates/collab/PROTOCOL.md` user-vocabulary section currently says (paraphrased):

> User says "update the framework" → Agent runs `collab-check`, then `npx ... init`, then reads UPGRADE_NOTES, then `--ack-upgrade`.

Replace with:

> User says: **"update the framework"** / **"update multi-agent-collab"** / **"upgrade to the latest version"**
>
> Agent runs:
>
> ```bash
> bash scripts/collab-update.sh   # OR: npx @gpgaoplane/multi-agent-collab update
> ```
>
> The command:
> 1. Compares installed vs. shipped version. Exits if already current.
> 2. Prints a summary and asks for confirmation (default: interactive).
> 3. Auto-backs up framework-managed files.
> 4. Runs the migration chain.
> 5. Writes `.collab/UPGRADE_NOTES.md`.
>
> Agent then:
> 6. Reads `.collab/UPGRADE_NOTES.md`.
> 7. Re-reads `AI_AGENTS.md` `behavioral-rules` (rules may have changed).
> 8. Reports the changes to the user.
> 9. Once user confirms they've absorbed the changes, runs `bash scripts/collab-update.sh --ack`.
>
> Other phrases:
> - "is there a new version" / "check for updates" → `update --check`
> - "preview the upgrade" / "show me what will change" → `update --diff-first`
> - "roll back the upgrade" / "undo the upgrade" → `update --rollback`
> - "ack the upgrade" / "archive the upgrade notes" → `update --ack`

### 4.1 Backward compatibility — known limitation

`re_init_shared` at `scripts/collab-init.sh:763-784` only `copy_file`s `templates/collab/PROTOCOL.md` to `.collab/PROTOCOL.md` if the target does NOT already exist (line 770: `[[ -f .collab/PROTOCOL.md ]] || copy_file ...`). Existing v0.4.x installs upgrading to v0.4.3 will NOT receive the new vocabulary text in their `.collab/PROTOCOL.md`.

**Functional impact:** none. The OLD vocabulary path (run `init`, read notes, run `--ack-upgrade`) is functionally identical to the new one (run `update`). Both reach the same end state — the new is just shorter to type / quicker for the agent to dispatch. Agents on existing installs will continue using the verbose 3-command sequence; agents on fresh v0.4.3+ installs use the 1-command sequence.

**Why we're NOT marker-refreshing PROTOCOL.md in v0.4.3:**

- Adding marker blocks to PROTOCOL.md vocabulary sections requires per-section markers (`vocab-handoff`, `vocab-rotation`, `vocab-upgrade`).
- Modifying `re_init_shared` to refresh PROTOCOL.md (sibling to AI_AGENTS.md treatment) is a small change.
- BUT: existing installs' `.collab/PROTOCOL.md` doesn't have the new markers, so refresh would no-op on them anyway. To make refresh effective, the 0.4.2-to-0.4.3 migration would need to detect old-format PROTOCOL.md and surgically inject markers via awk pattern matching — a complex migration with failure modes (user customizations might not match expected patterns).
- The cost-benefit doesn't justify this complexity for v0.4.3 since the functional contract is preserved.
- **Path forward:** a future v0.5.0+ migration can introduce markers if vocabulary tightening proves valuable enough to warrant the migration risk. By then, the framework will have more user-customization signal to weigh.

**What v0.4.3 ships:** new vocabulary in `templates/collab/PROTOCOL.md` (the source-of-truth file). Fresh installs at v0.4.3+ get it. Existing installs keep old vocab — fully functional, just verbose.

**README must call this out** in the v0.4.3 upgrade-guide section (per X4): for users who want the new vocabulary on existing installs, the manual fix is `cp $SKILL_ROOT/templates/collab/PROTOCOL.md .collab/PROTOCOL.md` (warning: blows away any user customizations to PROTOCOL.md).

## 13. Risks and mitigations

- **Confirm prompt blocks CI by default.** `update` without `--yes` in non-tty exits with helpful error (uses `[[ -t 0 ]]` per §3.1.1). Documented in `--help`, README, PROTOCOL.md.
- **`--diff-first` 2x runtime.** Opt-in only. README + help text call out the cost.
- **Cross-platform Windows.** `bin/cli.js` G2 fix already verified flag-forwarding works on Git Bash. The new `update` case follows the same `scriptArgs = rest` pattern. `read -r -p` is reliable on Git Bash.
- **Auto-confirmation by malicious agent.** Agent vocabulary in PROTOCOL.md does NOT include `--yes` for default phrases. An agent following the PROTOCOL would always invoke the interactive form. To bypass, an agent would have to deliberately add `--yes` — at which point the user is in agent-trust territory beyond what this plan can address.
- **Rollback sentinel staleness (CRITICAL).** Without §3.1.6's sentinel cleanup, post-rollback the next `update` would skip migrations because sentinels say "applied" while VERSION says pre-upgrade. Migrations would be no-ops for v0.4.x's no-op summary scripts; future migrations doing real work would silently skip. **§3.1.6 mandatory.** Tested by the "rollback then re-upgrade" case in §3.3.
- **Sourcing collab-init.sh under `set -euo pipefail`.** Sourcing executes top-level dispatch — would re-run argparse and mode dispatch as a side effect. **Resolution:** v0.4.3 commits to RE-EXEC pattern. `version_le` and `is_migration_applied` extracted to `scripts/lib/semver.sh` and `scripts/lib/migrations.sh` respectively (§3.1.5) so both scripts source the helpers without dragging in init's body.
- **Migration count display drift.** Pre-flight migration count must respect sentinels (sentinel-aware walk per §3.1, step 5). Otherwise we print "2 to apply" while 0 actually run. Tested by re-running update on already-applied state.
- **Confirmation prompt input handling.** Verbatim spec in §3.1.1 covers Y/y/yes/empty (accept), n/N/no/garbage (decline), non-tty (hard-fail). Tests cover all branches (§3.3).
- **Prior unacked UPGRADE_NOTES.md.** G5's auto-archive triggers correctly when `update` runs back-to-back without ack. No new behavior needed in this plan.
- **`update --check` masking real network errors.** `--check` reads cache only by design (per §3.1.8). Cache may be stale (24h TTL) or contain `check-failed:`. Spec covers all three cases. Future v0.5.0 may add `--check --refresh`.
- **PROTOCOL.md vocabulary refresh on existing installs.** Forward-only — existing installs keep old vocabulary, which is functionally equivalent to new (3-command vs 1-command, same end state). Per §4.1.
- **`update --rollback` restoring an unrelated backup.** "latest" backup may not be the most recent UPGRADE backup if user manually created one. Mitigation: print which backup is being restored before applying. Power users wanting specific control use `init --restore <id>`.
- **Concurrent `update` invocations.** Two agents/sessions running update simultaneously could race on backup, sentinel writes, UPGRADE_NOTES write. Mitigation: existing v0.4.2 G5 race-safe schema covers UPGRADE_NOTES. For backup directory: `do_backup` uses timestamp+seconds in the dir name; concurrent backups within the same second collide on the directory. Out of scope for this plan; v0.5.0 candidate (file-based lock at `.collab/.update.lock`).
- **First-run `update` against a v0.4.1 install.** v0.4.1's cli.js bug means `npx ... update --yes` doesn't forward `--yes`. v0.4.1 users must either: (a) call bash directly: `bash node_modules/@gpgaoplane/multi-agent-collab/scripts/collab-update.sh --yes`, or (b) upgrade to v0.4.2 FIRST via `npx ... init`, then use `update` from v0.4.2 onward. The v0.4.3 README must call this out explicitly (X4 covers this).
- **Bootstrap check before upgrade.** `update` exits non-zero on a non-bootstrapped repo (no `.collab/`) with `Run 'init' first.` (§3.1, step 1). Tests cover this case.
- **`npx ... update` first-call cost.** npx fetches the package tarball before dispatching. The "no network" promise of `--check` applies to its version-comparison logic only; npx itself may hit the network. Document in README that users wanting truly-no-network use `bash node_modules/.../collab-update.sh --check` directly.

## 15. End-to-end verification (post-merge, pre-tag)

Dogfood test sequence:

```bash
# 1. Create a tmp repo at v0.4.0 to simulate a downstream install.
TMP=$(mktemp -d)
cd "$TMP"
git init -q
COLLAB_AGENT=claude bash $SKILL_ROOT/scripts/collab-init.sh
echo "0.4.0" > .collab/VERSION

# 2. Run update --check.
bash $SKILL_ROOT/scripts/collab-update.sh --check
# Expect: "Installed: 0.4.0, Latest: 0.4.3, run 'update' to upgrade"
# Expect: .collab/VERSION still "0.4.0" (no state change)

# 3. Run update --yes.
bash $SKILL_ROOT/scripts/collab-update.sh --yes
# Expect: backup created at .collab/backup/0.4.0-to-0.4.3-<timestamp>/
# Expect: 3 migrations run (0.4.0→0.4.1, 0.4.1→0.4.2, 0.4.2→0.4.3)
# Expect: .collab/VERSION = "0.4.3"
# Expect: .collab/UPGRADE_NOTES.md written
# Expect: 3 sentinels in .collab/.migrations/

# 4. Run update --ack.
bash $SKILL_ROOT/scripts/collab-update.sh --ack
# Expect: UPGRADE_NOTES.md archived
# Expect: collab-check prints "OK: INDEX and filesystem aligned"

# 5. Run update --rollback.
bash $SKILL_ROOT/scripts/collab-update.sh --rollback
# Expect: .collab/VERSION reverts to "0.4.0"
# Expect: backup contents restored
# Expect: stale sentinels deleted (.collab/.migrations/0.4.0-to-0.4.1.applied,
#         0.4.1-to-0.4.2.applied, 0.4.2-to-0.4.3.applied — all gone after rollback)
# Expect: stdout includes "Removed 3 stale sentinel(s)."

# 5b. CRITICAL — verify re-upgrade after rollback runs migration BODIES (not just refresh).
bash $SKILL_ROOT/scripts/collab-update.sh --yes
# Expect: 3 migration bodies execute (visible >>> Upgrade summary blocks)
# Expect: .collab/UPGRADE_NOTES.md is written (proving migrations ran, not just re-init)
# Expect: 3 fresh sentinels appear in .collab/.migrations/
# This step would FAIL silently without §3.1.6's sentinel cleanup.

# 6. Run update --check after re-upgrade.
bash $SKILL_ROOT/scripts/collab-update.sh --check
# Expect: "Already up to date (0.4.3)."

# 7. Roll back AGAIN to test repeated rollback safety.
bash $SKILL_ROOT/scripts/collab-update.sh --rollback
echo y | bash $SKILL_ROOT/scripts/collab-update.sh --diff-first
# Expect: diff hunks printed (no state change yet)
# Expect: "Apply these changes? [Y/n]:" prompt
# Expect: after the printed 'y' is consumed, migrations apply
# Expect: final state same as step 3
```

If steps 2, 3, 4, 5, 5b, 6, 7 all behave as expected, the patch is shippable. **Step 5b is the load-bearing one** — it specifically gates against the rollback-sentinel-staleness bug surfaced in Plan-agent critique.
